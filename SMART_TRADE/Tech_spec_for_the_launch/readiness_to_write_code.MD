## Почему не 100%

До **100% готовности для режима «пишу код без единого уточнения»** не хватает нескольких конкретных фиксирующих решений, которые в пакете оставлены намеренно открытыми или как placeholders.

### Нужно уточнить (чтобы я писал без предположений)

1. **Технологический baseline для основной части backend**
   Нужно зафиксировать, что использовать как стандарт:
   - HTTP/API framework (например: FastAPI или другой),
   - scheduler/job orchestration (встроенный async scheduler / Celery / другой),
   - библиотеку валидации схем (pydantic/jsonschema),
   - HTTP client stack.

   Сейчас контуры описаны, но конкретный обязательный стек не закреплён как жёсткое правило.

2. **Строгий приоритет области первой поставки (MVP-код)**
   Нужно явно подтвердить, какие PART'ы пишем в первой волне как «основная часть».
   Предлагаю зафиксировать минимальный первый контур:
   - frame_engine
   - runtime_core
   - execution_bridge
   - webhook_receiver
   - case_memory
   - expectancy_monitor

3. **Режим запуска по рынкам/инструментам для первой версии**
   Подтвердить, что первая реализация жёстко ограничена baseline-ом:
   - Exchange: Binance Futures
   - Symbol: BTCUSDC
   - Timeframe: 1m

   Если нужно шире (мульти-символ/мульти-frame), это лучше зафиксировать сейчас.

4. **Формат хранения конфигов baseline в коде**
   Нужно зафиксировать, где истина конфигов в рантайме:
   - отдельные yaml/json файлы,
   - или env-only,
   - или гибрид (env + config files).

5. **Критерий “готово без тестов” для каждого модуля**
   Ты написал, что тесты сделаешь сам — ок.
   Тогда нужно зафиксировать минимальный DoD для кода без тестов:
   - какие CLI/ручные smoke-сценарии должны запускаться,
   - какие обязательные артефакты/логи должны появляться,
   - какие endpoint'ы должны быть функциональны в первой поставке.
